Lo que se explica en las siguientes secciones — el documento maestro y el backend con su documentación — es la base sobre la que se construye todo lo que el equipo hace ahora mismo.

2 · El documento maestro (2025-2)

Asignatura: Diseño y Desarrollo de Software Educativo I · Docente: Víctor Fabián Castro Pérez · Grupo: PLAN B · Equipo en ese momento: Jeider Jair Gómez Oviedo y Pedro Gabriel Romero Mendivil.

Documento: Especificación de Requisitos de Software (SRS) de STIRE

Es el documento donde el proyecto se definió por primera vez de forma formal: contiene la reseña del proyecto, la descripción de la propuesta, el propósito y alcance, las definiciones y acrónimos, y los requisitos funcionales y no funcionales del sistema. Todo lo que el backend construye desde entonces es una implementación de lo que este documento especificó.

Lo que definió y sigue vigente hoy

  • STIRE = Sistema Tutor Inteligente con Repetición Espaciada.
  • Asignatura objetivo del sistema: Fundamentos de Algoritmia.
  • Un tutor conversacional que explica conceptos, resuelve dudas, sugiere ejercicios de práctica, recomienda qué repasar y orienta el estudio — no reemplaza al docente, acompaña el aprendizaje autónomo fuera del aula.
  • Los cinco estados de aprendizaje por unidad, mostrados en el Gráfico G2 más abajo.
  • La lógica de repetición espaciada para priorizar qué se repasa primero.
  • Las unidades de aprendizaje del curso: Variables, Tipos de datos, Condicionales, Ciclos, Arreglos.

3 · El backend y su documentación (2026-1)

Asignatura: Diseño y Desarrollo de Software Educativo II · Docente: Alí

El profesor probaba el proyecto apoyándose en Claude, revisaba el modelo entidad-relación y le señalaba al equipo qué debía mejorar. El equipo llevaba esas observaciones al código y documentaba el sistema en la carpeta docs/ del repositorio — la misma carpeta que hoy contiene, además, toda la documentación de las olas de remediación de seguridad y las auditorías técnicas del proyecto.

Carpeta completa: github.com/Jeider-Gomez/Stire-Soft/tree/main/docs

Nota de precisión. Tres de los cinco documentos de abajo (01, 02 y 04) contienen hoy afirmaciones desactualizadas que dicen que el sistema ejecuta el código del estudiante en contenedores Docker. Es falso: el sistema usa un sandbox propio, con aislamiento de proceso del sistema operativo, sin Docker. El hallazgo — 12 afirmaciones falsas y un log de ejemplo fabricado en 02_FLUJOS_Y_OPERACIONES.md — ya está registrado con corrección programada para el 31 de agosto (ver bitácora y MONITOREO_SEMANAL.md, sección 3). Las descripciones de abajo describen la arquitectura real del sandbox, no lo que esos documentos afirman todavía.
00_VISION_FUNCIONAL.md

¿Por qué existe STIRE?

La visión pedagógica del proyecto: el problema que resuelve, la propuesta de valor, los actores del sistema (estudiante, docente, tutor IA) y el ciclo cognitivo del estudiante a través de los cinco estados de aprendizaje. Es el primer documento a leer — para cualquiera, técnico o no, que necesite entender el propósito del sistema antes que su implementación.

Ver en GitHub

01_ARQUITECTURA_Y_DISENO.md

¿Qué es STIRE técnicamente?

La arquitectura del sistema: el patrón de diseño orientado al dominio (DDD), el registro de decisiones de arquitectura (ADR) y el esquema relacional completo de la base de datos — el mismo modelo entidad-relación que el docente Alí revisaba semestre a semestre. El sandbox de ejecución de código que describe hoy como basado en Docker en realidad corre por aislamiento de proceso del sistema operativo, sin Docker.

Ver en GitHub

02_FLUJOS_Y_OPERACIONES.md

¿Cómo funciona STIRE?

El recorrido operativo del sistema: qué hace un estudiante paso a paso, qué hace un docente paso a paso, y cómo se puede seguir la traza de lo que ocurre en el sistema de principio a fin. La calificación de código, aunque este documento la describa hoy con un ejemplo de un contenedor Docker, corre en realidad sobre el mismo sandbox de proceso del sistema operativo mencionado arriba — ese ejemplo de log no corresponde a una ejecución real del sistema.

Ver en GitHub

03_MOTOR_Y_TUTOR.md

¿Cuál es el cerebro de STIRE?

El motor de evaluación de respuestas, el motor que ejecuta y califica el código que entrega el estudiante, el cálculo de dominio (mastery), el algoritmo de repetición espaciada SM-2, y el tutor con inteligencia artificial. Es el documento más denso técnicamente — para quien necesite entender los algoritmos, no solo la arquitectura general.

Ver en GitHub

04_ESTANDARES_Y_SEGURIDAD.md

¿Cuáles son las reglas del juego?

Las convenciones de código del proyecto, el modelo de seguridad (autenticación, protección contra XSS, aislamiento del sandbox de ejecución), consideraciones de escalabilidad, y la deuda técnica que el propio equipo reconoce abierta. Aquí también aparecen, todavía sin corregir, algunas de las menciones a Docker señaladas en la nota de arriba.

Cuellos de botella y decisiones tomadas

  • Las fichas de las 7 categorías de MODESEC no se iniciaron esta semana. Primero había que cerrar el inventario definitivo de ventanas del sistema; sin él, las fichas habrían quedado desalineadas con el Mapa de Navegación. Se pasaron a la semana siguiente por decisión de orden de trabajo, no por retraso.
  • Niveles muy distintos de manejo de Git dentro del equipo estaban frenando el trabajo de diseño. El equipo decidió eliminar las reglas estrictas de control de versiones (ramas, revisiones cruzadas, convenciones de mensajes): basta con que el archivo esté subido al repositorio antes del viernes, y quien no maneje Git le entrega el archivo a un compañero para que lo suba. Se conserva solo el mensaje de commit que exige la guía del curso.

Ayuda solicitada al docente

  • La Ventana Estándar: ¿se espera una única maqueta modelo que represente el estándar visual del sistema, o una maqueta por cada tipo de ventana?
  • En las 7 categorías (Imagen, Nombre de ventana, Texto, Audio, Video, Animación, Acciones): ¿es válido declarar "No aplica" con justificación pedagógica cuando la ventana no contempla audio o video?
  • El pitch de 60 segundos: ¿lo sustenta un solo integrante o se espera que los cinco intervengan repartiéndose los cuatro bloques?
